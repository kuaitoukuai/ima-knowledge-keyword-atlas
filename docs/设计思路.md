# 设计思路

这份文档记录这个项目**为什么长成现在这样**。代码可以重写，但这些取舍值得保留。

---

## 一、起点：一个具体的小麻烦

用 AI 记笔记的人会经历同一个循环：

1. 每次对话结束，把总结丢进知识库 —— 很爽
2. 攒到几百篇，开始记不住里面有什么
3. 想回顾时，面对的是几百个文件名
4. 于是又开一次对话让 AI「总结一下」—— 得到一段流畅但**无法验证**的文字
5. 下周再问，得到另一段不一样的文字

问题不在于 AI 写得不好，而在于**输出没有结构、无法校验、不能拆开用**。

这个项目想做的，是把第 4 步换成一条**可重复、可验证、可迭代**的流水线。

---

## 二、三个核心判断

### 判断 1：结构比文字重要

一段 2000 字的「半年总结」和一张 10×10 的关键词表，信息量可能差不多，
但后者可以**筛选、可以打印、可以逐格追问出处**。

所以第一版就定死了三层结构：**维度 → 父关键词 → 子关键词**。

- 维度：视角（决定这张表好不好用）
- 父关键词：可记忆的锚点（4~10 字）
- 子关键词：具体的「坑」和「做法」

### 判断 2：可溯源是底线，不是加分项

如果一条结论指不回原文，它对读者就是**不可信**的。

所以：
- 每条子关键词必须带 `src`（来源文件名）
- `05_merge_validate.py` 会逐个检查文件是否真实存在
- 出表时额外给一张「文档溯源索引」，列出**全部**源文档，标明哪些被引用、哪些没有

这条设计拦住的最典型错误：模型编出一个格式完全正确的文件名（比如 `2026-09-18_采集优化_ai问答.md`），
但磁盘上根本没有这个文件。**模型自查发现不了，文件系统可以。**

### 判断 3：确定性交给脚本，判断力交给模型

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 翻页、下载、重试、限流退避 | 脚本 | 确定性操作，模型做只会引入不确定性 |
| 抽取标题 / 小标题 / 要点原句 | 脚本 | 正则就够，且 510 篇的成本是 0 token |
| 聚类 | 脚本 | 关键词匹配即可，还可复现 |
| 分哪几个维度 | **模型** | 需要理解内容，且要跟用户确认视角 |
| 父/子关键词怎么命名 | **模型** | 需要概括能力 |
| 校验文件存在性 | 脚本 | 不能靠模型自查 |
| Excel 行高、打印设置 | 脚本 | 纯计算 |

一个反直觉的结论：**让模型少干点活，整体质量反而更高。**
模型只做「需要理解」的那一小部分，剩下的交给可测试的代码。

## 三、读不完的问题怎么解

510 篇文档，平均每篇几千字，全读进上下文不可能。

解法是**两级阅读**：

```
全量 510 篇
   ↓ 03_index_docs.py（正则抽取，0 token）
结构索引（每篇 20~40 行：小标题 / 要点原句 / 强调词）
   ↓ 按维度聚类 + 取相关度前 32 篇
紧凑摘要（每维度一份，约 15 KB）
   ↓ 子代理读摘要
父关键词 → 3~7 个子关键词
   ↓ 证据不足时 grep 原文下钻
```

关键是**摘要里保留了完整文件名和原文措辞**，所以子代理既能快速定位，又能在需要时精确回溯。

实测：32 篇的紧凑摘要只能覆盖约一半的父关键词，另一半必须靠 grep 原文补齐。
所以在子代理提示词里**必须明确给出「下钻原文」的许可与路径**——这条经验是踩出来的。

## 四、并行子代理的边界

10 个维度拆给 5 个子代理（每个 2 维度）并行跑。这样做的收益不只是快：

- 每个代理的上下文更聚焦，摘要读得更细
- 单个代理失败可以只重跑那 2 个维度
- 输出格式用严格 JSON 约束，事后脚本校验

代价是**格式不一致的风险**。对策有三条：

1. 提示词里写死 JSON schema，并明确「不要 markdown 代码围栏」（子代理很爱加 ```` ``` ````）
2. 要求 `src` 从摘要里**原样复制**
3. Phase E 统一校验，不通过就重跑，不带错误往下走

## 五、Excel 为什么做 6 个视图

同一份数据，不同的使用场景需要不同的切法：

| 场景 | 需要什么 | 对应视图 |
|---|---|---|
| 「一眼看全貌」 | 压缩到最小、能打印贴墙 | ① 总览矩阵 |
| 「我要看每个关键词下面有什么」 | 展开但不脱离网格 | ①B 含子关键词总览 |
| 「逐条通读一遍」 | 一行一个父关键词 | ② 关键词展开 |
| 「我想搜某个概念」 | 一行一条、可筛选 | ③ 子关键词明细 |
| 「这条结论出自哪？」 | 反查出处 | ④ 文档溯源索引 |
| 「结构均衡吗？」 | 统计 | ⑤ 维度统计 |

做 6 个不是为了炫技，而是因为**一份表服务不了 6 种用法**。

## 六、几个被现实教育过的决定

### 不要写 Excel 公式（除非确认环境能重算）

openpyxl 写的公式只是字符串、没有缓存值。`pandas`、`data_only=True`、
以及多数在线预览器（微信/邮件附件预览）读到的都是**空白**。

只有在环境里跑过 `recalc.py` 并拿到 `status=success`，才能用公式。
否则**在 Python 里算好结果写死**。这类速览表本来就是静态的。

### 一页纸放不下就别硬压

把 579 个子关键词塞进 10×10 网格，A4 横向要 **约 2.6 页**。
强行 `fitToHeight=1` 会把字号压到 5pt 左右，等于不可读。

正确做法：`fitToWidth=1` + `fitToHeight=0` 让它续页，**并把页数如实告诉用户**。

### 交付前先试试目标文件能不能写

用户在预览器/Excel 里开着这个文件时，`wb.save()` 会 `PermissionError`，
删掉 `~$xxx.xlsx` 锁文件也无效（锁属主是外部进程）。

脚本里 try/except，失败就另存 `<name>_v2.xlsx` 并明确告知——**不要静默失败**。

### 边界要写进交付物

不确定的事要说出来。例如某个父关键词在语料里找不到证据时，
不硬凑、不编造，而是在汇报里说明「这一条在 510 篇里没有直接证据，
按最接近的真实文档落子」。用户据此可以补充语料或调整关键词。

## 七、如果要继续往下做

几个还没做但值得做的方向：

- **增量更新**：知识库新增笔记后，只重跑受影响的维度
- **回溯语料**：把 `src` 里的原文片段自动摘录进明细表，省去翻文件
- **多视角对比**：同一批语料同时生成「技术技能」和「业务领域」两套体系，看差异
- **可视化**：把维度×关键词做成热力图或关系图
- **导出 Markdown / CSV**：方便再导入其他知识库
