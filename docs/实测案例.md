# 实测案例

一次真实的端到端运行记录。所有数字都是实测值，不是估算。

---

## 一、输入

| 项 | 值 |
|---|---|
| 数据源 | IMA 知识库中的一个个人笔记库 |
| 文档数 | **510 篇** Markdown |
| 总体积 | 约 6.3 MB |
| 时间跨度 | 约 5 个月（2026-05 ~ 2026-10） |
| 文档性质 | AI 对话总结：含工作日志、问题排查记录、技术方案、版本汇总等 |

> 命名特点：大量文档带日期前缀与主题后缀（如 `2026-10-09_20261010080228.md`），
> 且存在同一内容的多份副本（不同时间戳）。510 篇里真正独立的主题远少于 510。

---

## 二、各阶段实测

### Phase A · 拉取

| 指标 | 值 |
|---|---|
| 清单条数 | 510（分 11 页拉取） |
| 下载成功 | 510 篇，**0 失败** |
| 首次尝试 | 并发 8 → **242 篇被限流**（接口返回空 URL） |
| 修正后 | 并发 3 + 每篇最多 4 次重试（退避 2/4/6/8 s）→ 100% 成功 |
| 耗时 | 约 12 分钟（含重试） |

**这条经验写进了 `02_fetch_docs.sh`**：并发上限 3，且脚本可反复重跑补漏。

### Phase B · 建索引

| 指标 | 值 |
|---|---|
| 产出 | `index.json` + 13 个索引包（每包 40 篇） |
| 索引包总体积 | 约 1.6 MB（原文档 6.3 MB，压缩到 1/4） |
| 抽取内容 | 标题、日期、小标题、问题/原因/解决类原句、强调词 |

索引包可以整包读进上下文，这是「读完全部 510 篇」在工程上可行的前提。

| Bug 排查与根因定位 | 311 |
| 测试与质量保障 | 246 |
| 部署分发与运维 | 219 |
| 多机网络与凭据管理 | 218 |
| 爬虫与反爬攻坚 | 202 |

### Phase D · 并行细读

## 四、一个维度的示例（脱敏后）

以「编程与代码基本功」为例，展示父关键词与子关键词的层级关系与溯源粒度：

| 父关键词 | 子关键词（节选） | 来源文档（节选） |
|---|---|---|
| 参数名格式一致 | `price` 而非 `product_price`；`html` 遮蔽标准库；`pageNo` 与 `pageIndex` 混用 | 版本汇总 / Bug 修复记录 |
| 空值与除零保护 | 除零守卫查错对象；分母空值返回空白；`Decimal InvalidOperation` 未捕获 | 对抗性检查报告 |
| 上下文管理器 | `fitz` 需显式 close；`_get_conn` 连接泄漏；异常路径也要释放 | Bug 修复记录 |
| 编码乱码排查 | PowerShell 5.1 默认 GBK；`.ps1` 中文字面量按 ANSI 读；NFKC 归一化引入非法字符 | 电子书批处理全记录 |

> 完整的 100 个父关键词与 579 个子关键词**不包含在本仓库中**——
> 它由使用者自己的语料与视角决定，这正是本项目的用法：**你喂什么语料、选什么视角，就产出什么体系**。

## 五、可复制的用法建议

1. **先小后大**：第一次跑建议先取 50~100 篇试一遍全流程，确认视角与关键词粒度合适，再上全量。
2. **视角先定**：本案例里第一版按「项目」分维度，第二版改成「个人技术技能」，整表重做。确认视角再开跑。
3. **允许重复引用**：天然只有一个权威来源的关键词（如某个算法），让多个子项引用同一篇文档，好过硬拆到弱相关文档。
4. **接受部分文档不被引用**：510 篇里 389 篇没被引用是正常的，其中很多是同内容副本。
5. **迭代只重跑后半段**：改关键词不必重新下载，从 Phase D 或 E 开始即可。
