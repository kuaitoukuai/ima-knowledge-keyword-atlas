# 子代理提示词模板（Phase D 用）

> 每个子代理负责 1~2 个维度。把 `{{...}}` 占位符替换掉后直接作为 Agent 提示词发送。
> 5 个子代理**并行**发出（一条消息里多个 Agent 调用），比串行快得多。

---

```
你是中文技术内容分析师。任务：把「{{维度A中文名}}」「{{维度B中文名}}」两个维度的 {{N}} 个父关键词，
各自展开为 3~7 个子关键词，并且**每个子关键词必须能溯源到一篇真实的 md 文档**。

## 数据位置（都在本机磁盘）
- 工作目录：`{{工作目录}}`
- 全量原始文档目录：`{{工作目录}}/md/`（共 {{总篇数}} 篇 md，文件名形如 `045_取数通道与人机验证会话恢复_设计与测试报告.md`）
- 已聚类的紧凑摘要（**先读这两个**）：
  - `{{工作目录}}/digest/c/{{D01}}.md`
  - `{{工作目录}}/digest/c/{{D02}}.md`
- 全部文档的结构索引（需要更多线索时用 Grep 搜）：`{{工作目录}}/index/index.json`

## 需要展开的父关键词（必须全部覆盖，共 {{N}} 个）
{{维度A中文名}}：
1. {{父关键词1}}
2. {{父关键词2}}
...（10 个）

{{维度B中文名}}：
11. {{父关键词11}}
...（10 个）

## 方法
1. 先完整读 `digest/c/` 下的两份摘要。摘要里每篇文档给出了：完整文件名、标题、日期、`· 小标题`、`> 要点原句`。
2. 对每个父关键词，从摘要中找出**真实对应的技术点**。必要时打开 `md/` 下的原文（Read 工具）核实细节与措辞。
3. 每个父关键词产出 **3~7 个**子关键词。子关键词要具体、可辨识，优先写成「踩的坑 / 采取的做法」，
   长度 **3~12 个汉字**（可含必要英文术语，如 `Decimal`、`429`、`MCP`）。
4. 每个子关键词必须给出一条 `note`（≤28 字，说明这是什么问题或做法）
   和一条 `src`（**必须是 `md/` 下真实存在的完整文件名**，从摘要里原样复制，不要自己编）。
5. 若某个父关键词在摘要前 32 篇中证据不足，可用 Grep 在 `md/` 或 `index/index.json` 里检索关键词找支撑文档，
   但 `src` 仍必须是真实文件名。
6. **不许编造**：不能虚构文件名或技术点。确实找不到证据时，选最接近的真实文档来支撑，并在汇报里说明。

## 输出（严格）
把结果写成 JSON 文件：`{{工作目录}}/expand/{{D01}}_{{D02}}.json`

结构（UTF-8，不要 BOM，不要 markdown 代码围栏）：
{
  "dimensions": [
    {"dim": "{{D01}}", "dimName": "{{维度A中文名}}",
     "parents": [
       {"parent": "{{父关键词1}}",
        "subs": [{"kw": "...", "note": "...", "src": "123_xxx.md"}]}
     ]}
  ]
}

要求：{{N}} 个 parent 一个不少；每个 parent 的 subs 数量在 3~7 之间；所有 src 都是真实文件名。

最后用一段话汇报：完成了几维几个父关键词、总共多少子关键词、遇到的困难。
```

---

## 为什么这样写

| 提示词里的约束 | 对应的问题 |
|---|---|
| 「先读 digest/c，不够再下钻原文」 | 只读摘要会浮于表面，只读原文会爆上下文；两级推进最省 |
| 「src 必须是真实存在的完整文件名，不要自己编」 | LLM 最容易在这里幻觉，凭空造出看似合理的文件名 |
| 「JSON、无 BOM、无代码围栏」 | 子代理经常套 ``` 围栏，导致后续解析失败 |
| 「最后汇报困难」 | 让你能发现哪些父关键词证据薄弱，及时调整 taxonomy |
| 3~12 个汉字 | 太短无信息量，太长格子放不下 |

## 实测出来的两个坑

1. **摘要覆盖不足是常态。** 32 篇摘要通常只能覆盖一半左右的父关键词，另外一半要靠 Grep 原文。
   所以在提示词里必须明确给出「下钻原文」的许可与路径。
2. **同一技术点散落在多篇里。** 让子代理为同一父关键词的不同子项**分配不同文档**作 src，可溯源性更好；
   但如果是天然只有一篇权威文档（如某个算法），允许重复引用，不要硬拆到弱相关文档上。
