# 六阶段工作流（从知识库到关键词体系 Excel）

> 整体思路：先把**全量文档**变成机器可读的结构索引 → 派并行子代理**逐维度细读** → 硬校验之后才建表。
> 不要把「读文档」和「写 Excel」混在一起，中间必须有可校验的结构化产物。

---

## Phase 0 — 准备

确认三件事：

1. **目标知识库**（名称或 kb_id）
2. **工作目录**（后面所有中间产物都落在这里，建议 `<workspace>/kb-atlas/`）
3. **视角**（决定维度怎么分）。视角不同，同一批文档会得出完全不同的关键词体系。常见视角：
   - **技术技能视角**：编程基本功 / Bug 排查 / 爬虫反爬 / 部署运维 / 测试质量 / 工程方法 …
   - **业务领域视角**：获客 / 交付 / 财务 / 人力 / 合规 …
   - **问题-解法视角**：按「遇到什么问题 → 怎么解决」组织
   - **时间/项目视角**：按项目或阶段组织（注意：一次性任务多的场景，这个视角价值低）

> 视角要**先跟用户确认**。这是最容易返工的一步 —— 本 skill 的诞生场景里，用户第一版按「项目」分，第二版改成「个人技术技能」，整表重做。

## Phase A — 拉取全量

```bash
bash scripts/01_list_kb.sh "<知识库名称>" "$WD/list.jsonl"
bash scripts/02_fetch_docs.sh "$WD/list.jsonl" "$WD/md" 3
```

- `01` 支持翻页，遇到 `is_end` 停止；输出 JSONL，每行一条。
- `02` **并发务必 ≤3**。并发 8 时实测 510 篇有 242 篇被限流（`get_media_info` 返回空 URL）。脚本已内置 4 次重试与跳过已下载文件，可反复重跑补齐。
- 结束后 `ls "$WD/md" | wc -l` 应与清单条数一致。

## Phase B — 建结构索引 + 确定维度

```bash
python3 scripts/03_index_docs.py --src "$WD/md" --out "$WD/index" --per-pack 40
```

产出 `index.json`（每篇的标题/日期/小标题/要点原句/强调词）与 `pack_NN.md`。

**然后通读 `pack_*.md`**（每包 40 篇，一包几十 KB，可以整包读进上下文，不会爆）。目标是产出 `taxonomy.json`：

```json
{
  "dimensions": [
    {"dim": "D01", "dimName": "编程与代码基本功",
     "match": ["语法","异常","编码","正则","精度"],
     "parents": ["参数名格式一致","Decimal 精度处理","…10 个"]}
  ]
}
```

要点：
- **`match`** 是给聚类脚本用的检索词（越具体越好，20~30 个）；**`parents`** 是最终要展示的父关键词。
- 维度数与每维关键词数由用户定。常见规格：**10 × 10 = 100**（正好一页纸）；也可 8×6、12×8 等。
- 父关键词写成**短名词短语**（4~10 个汉字），让格子能放下；「问题 → 方法」式最耐读（如「静默降级识别」「先证明再下结论」）。
- 维度名尽量押韵/对称，读起来像体系而不是清单。

## Phase C — 按维度聚类出摘要

```bash
python3 scripts/04_cluster_digest.py --index "$WD/index/index.json" \
    --taxonomy "$WD/taxonomy.json" --out "$WD/digest" --top 32
```

- `digest/Dxx.md`：该维度全部命中文档（可很长）
- `digest/c/Dxx.md`：相关度前 32 篇的紧凑版（**这是给子代理读的**）

自检：每个维度命中篇数不能太少（<15 说明 `match` 词太窄），也不能是全部（说明太宽）。

## Phase D — 并行细读，展开子关键词

按每 1~2 个维度一组的粒度，**并行**派子代理（10 维度 = 5 个代理）。每个代理拿到：
某个维度的 `digest/c/Dxx.md` 路径、该维度 10 个父关键词、md 目录路径。

**提示词模板见 `references/subagent-prompt.md`（直接复制改维度名即可）。**

产出：每个代理写一个 JSON 到 `$WD/expand/`，结构：

```json
{"dimensions":[{"dim":"D01","dimName":"编程与代码基本功",
  "parents":[{"parent":"参数名格式一致",
    "subs":[{"kw":"price 而非 product_price","note":"参数命名踩坑","src":"123_xxx.md"}]}]}]}
```

硬性要求（写进提示词里）：
- 每个父关键词 **3~7 个子关键词**，每个 **3~12 个汉字**（可含必要英文术语）
- 每条必须有 `note`（≤28 字说明这是什么问题/做法）和 `src`（**md 目录下真实存在的完整文件名**）
- 摘要不够就去 `md/` 原文里 grep 取证；**不许编造文件名或技术点**

## Phase E — 合并 + 硬校验（不可跳过）

```bash
python3 scripts/05_merge_validate.py --expand "$WD/expand" --taxonomy "$WD/taxonomy.json" \
    --md "$WD/md" --out "$WD/merged.json"
```

校验三件事，任一不过就报错退出：父关键词集合与 taxonomy 完全一致、子关键词数在区间内、**每条 src 真实存在**。

> 这一步是质量闸门。LLM 生成结构时最典型的失败就是**编造来源文件名**和**父关键词漂移**（少一个/多一个）。不校验就建表，错误会一路带到交付物里。

## Phase F — 渲染 Excel

```bash
python3 scripts/06_build_workbook.py --merged "$WD/merged.json" --md "$WD/md" \
    --out "$WD/关键词体系.xlsx" --title "<标题>" --subtitle "<统计区间｜来源｜口径>"
```

一次产出 6 个视图（矩阵总览 / 含子关键词总览 / 展开 / 明细 / 溯源 / 统计）。

## Phase G — 交付前自检清单

- [ ] 总览矩阵格子数 == 维度数 × 每维关键词数，且无空格
- [ ] 明细行数 == 子关键词总数，无空值
- [ ] 溯源表行数 == md 目录文件数；被引用数 >0
- [ ] 用 `openpyxl.load_workbook(..., rich_text=True)` 抽查一个富文本格子，确认父关键词 `b=True`
- [ ] 打印：总览页 A4 横向 fitToPage 1×1；含子关键词页会纵向续页（正常，不要强行压一页）
- [ ] 把「页码/续页」如实告诉用户，不要假装一页装得下

## 规模参考（本 skill 实测基准）

| 指标 | 数值 |
|---|---|
| 源文档 | 510 篇 md，约 6.3 MB |
| 索引 + 摘要中间产物 | 约 5 MB |
| 维度 / 父关键词 / 子关键词 | 10 / 100 / 579 |
| 被引用文档 | 121 篇（其余为重复副本或非证据文档） |
| 端到端耗时 | 下载约 12 min（含重试）、其余约 10 min |
